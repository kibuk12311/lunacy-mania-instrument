# Changelog

## 0.10.0

- **Saved analyses survive updates** («А анализ карт для сессии всегда будет анализировать? Нельзя это сохранять?»): the shared result cache lived in a folder per app version (results-0.9.8 held 8796 results, 0.9.9 began again from nothing) and the Session library marked every analysis stale after any update, so each update analysed everything again. Both now follow an **analyzer fingerprint** (src/core/analyzerVersion.js, worked out at start in about 60 ms): a hash of the analysis code reachable from the card's dan, the details and the dan by part (73 files), what it loads at run time (the dan model, MinaCalc's wasm, Companella's model and its ONNX runtime), the 6 texts a result is worded with and a format number — not the UI or any other text. The cache is userData\results-<fingerprint>; on the first start the newest results-<version> of the same analyzer is renamed into place, the results of older ones of the same analyzer are moved in where missing, and the app's other result folders are removed (app/resultsFolder.js, told in log.txt). Which release had which analyzer is a table made from the release commits (tools/analyzer-fingerprints.mjs → src/core/analyzerReleases.js): 0.9.7, 0.9.8 and 0.9.9 share one, so the update from them keeps every result and the Session library keeps its analyses; only a changed analyzer marks them for redoing (still usable meanwhile).
- **Analysis about 3× faster, same numbers** («А нельзя ускорить для всех анализ карт?»): one .osu parse shared by Sunny, Daniel, Azusa and Interlude, no repeated estimator runs (Daniel ran 5–6 times a chart, Sunny 3, Roxy twice), and Sunny / Daniel's inner loops without allocations or binary searches (vendor/leoblack, each change marked «Lunacy mania»). One chart: mean 180 → 57 ms, p90 322 → 104 ms. Every result is bit-identical: tools/bench-analyze.mjs, 1200 cases of 600 real maps old vs new in separate processes (card, details, dan by part), and an independent review with ~4000 adversarial cases. So the saved results stay: src/core/analyzerSameResults.js maps this analyzer to 0.9.9's, nothing is analysed again.
- **Huge charts no longer fail:** past ~120 000 objects (a 2-hour marathon) the analysis, its details and a marathon of it stopped with "Maximum call stack size exceeded" (Math.min(...times) and the like); minOf / maxOf fold the same pairwise Math.min / Math.max. A Session-library map that failed is tried once more by a new build.
- **osu! lazer is read** («Сделай чтение lazer для сессии и профиля»): lazer keeps its library and scores in a realm database (client.realm), so the app reads a copy of it — never the file itself — with realm 20.2.0 in a utility process (app/lazerRealm.js, app/lazerRealmWorker.js, src/lazer/realmDump.js): lazer's data folder from %APPDATA%\osu\storage.ini (FullPath) or %APPDATA%\osu, the copy in a temp folder of ours removed right after, opened read-only; mania maps (not hidden, not deleted) and scores, cached until client.realm changes, one read at a time, 60 s limit. On a real library: 5840 4K maps and 359 scores in about 0.5 s. Only realm's Windows runtime is packed (4.5 MB unpacked, no Android/Apple builds).
- **Session: lazer's 4K maps are a source** like stable's Songs and Interlude: the same .osu in stable or Interlude is one map with both sources; the app's own rate and marathon copies are skipped; «osu! lazer: N» on the library line; a lazer-only map goes into a marathon through a copy in Documents\<app>\lazer (lazer's files only read). The collection export still takes stable maps only.
- **Profile: «Импорт из osu! lazer» / "Import from osu! lazer"** beside the stable and Interlude imports: the main player's 4K plays at a fixed rate (DT/NC/HT/DC with their speed; wind up/down and adaptive speed skipped), judgements, combo, a fail kept as a fail; a play on a map lazer has updated since, or on a converted osu! map, is skipped. A play the live recording already took from tosu is not added twice (same map, rate and judgements).
- **Background analysis on several cores** («А нельзя ускорить для всех анализ карт?»): every background analysis (the Session library, the Picks' rate fits, the rate ladder, the card's strain line and dan by part, the profile imports, the auto-marathon, the overlay's Dan) went through one line on the card's worker, one map at a time. The line now runs on a small pool of workers of its own (app/workerPool.js, app/analysisPoolWorker.js: the analysis jobs only, no generator): the cores less two and no more than the memory takes (4 GB left to the rest, a worker for every 2 GB beyond: 8 GB two, 6 GB one), at most four (none with two cores or 5 GB or less, where it stays as before), and no worker more while less than 1 GB is free; started with the first job and stopped after 30 s with nothing to do, at below-normal priority so the card, the window and the game come first, with a smaller V8 young generation (about 210 MB a worker at the most over long charts instead of 270–280; V8 flags reach a utility process only through --js-flags). The card's own worker now takes only the card and the rate preview, so they never wait behind a background analysis; a chart the card and a background job ask for at once is analysed once, and if the pool's worker fails it, the card's worker tries. Results go to the same shared cache; stale background jobs are still dropped before they start. The callers with independent maps keep that many under way: the Session library (pause stops new maps, a resume brings every lane back; the save every 100 maps or 15 s and the progress as before), the rate ladder (rows still in order), the plan's «рейты» (up to 4 cards at once; the downloads stay one by one) and the profile imports (the plays still added in order). The card's own analysis starts one pool worker ahead when none is running, so the strain line after it does not wait for a process to start (details 75–82 ms instead of 219–243 ms on a pool that had gone idle). Measured with tools/bench-library.mjs on top of the faster analyzer (Ryzen 7 9800X3D, 8 cores / 16 threads, synthetic maps): the Session library 17.3–18.2 → 39–46 maps a second; the plan's rates 2.9 → 4.5–5.6 cards a second for 12 cards and 3.2 → 6.7–6.9 for 24 (one card's own fit is still one search, about as long as before); the card while the library runs 75 ms median, 91–94 ms p95 (before 65 ms, 110–115 ms p95; 60–69 ms with nothing else running).
- **Settings: the author once** («У тебя 2 раза повторяется Автор Sneezey»): the line under About repeated About's own; it is gone.

## 0.9.8

- **The Create tab's dan ceiling is gone** («часто редактор создаёт 3-7 дан и не выше»). Measured first (tools/eval-dan-range.mjs, read-only on 5 held-out songs of eval-v3/heldout-179 at 135, 171, 190, 210 and 243 BPM, the app's own analyser, every model, asked 5 / 8 / 11 / 13 / 15 / 17 as a one-dan range): the generator's search only moved one density knob, and that knob was capped at +1 (a second try at +2.5 only when the dan fell over half a dan short; nn-v2's span −2…+1); the grid stayed 1/4 unless the player ticked other grids, so a slow song could not get denser than 4 rows a beat; the row sizes stayed the family's own (the size model may bend them only ×1.5); and the light parts were held down by the contrast term. Result: a 135 BPM jumpstream song gave dan 2.4–5.6 whatever was asked (its human map is 12.7), 190 and 243 BPM songs stopped at 12–13, and over all runs only 59 of 120 landed in range (22 of 60 asked 13+), mean miss 2.4 dans.
- **Closed-loop targeting (src/gen/targeting.js):** a map that comes out short of its range is made again on up to three rungs that lift those limits (generateLearned.js `opts.boost`): the knob's top (3 / 5 / 8, also for parts with their own range), the light parts' contrast (×0.5 / 0.25 / 0), a chord weight (rows of more notes weigh e^(0.5 / 1 / 1.6 × extra notes), up to the family's room: streams ±1 note at half strength, jumpstream 2, handstream 3, chordjack 4), the dan the model is conditioned on (+0.5 / 1.5 / 3) and the grids (1/8, then 1/6 and 1/3 with a lean towards the finer grid: a lower bar over the 1/4 evidence and noise floor, 1/3 beats turned into 1/6, a divisor head's finer classes ×3) — but only grids whose rows stay at most 20 per second at the song's tempo (1/8 up to 150 BPM, 1/6 up to 200). How far short the plain map is picks the first rung; a rung that goes over the range gets one try halfway; the closest map wins. A map far over its range gets one lighter try (fewer chords, a lower knob and conditioning). 30 s budget in the worker (main sends it; the window cannot), each next try only when it fits. The playability guard is untouched (jack limits per family, nothing faster than 65 ms in one column outside jack patterns), so a boosted map plays by the same rules (0.7 awkward spots per map against 0.3 plain, max streamy jack 2 in both).
- **After, same songs and seeds:** 84 of 120 in range (34 of 60 asked 13+), mean miss 1.0 dans; per model, mean dan asked 15 → 13.5 / 13.7 / 14.0 / 13.3 (Classic / XGBoost v3 / S / M; before 11.4 / 11.6 / 13.1 / 11.8), asked 17 → 14.6 / 14.9 / 15.2 / 15.2 (before 11.9 / 12.0 / 13.3 / 13.2); the 135 BPM song now reaches 12.4 (was 5.6), the 190 BPM one 18.7 (was 15.1). Median 2.7 s per map (p90 7.9 s) in the eval, against 1.7 s before; only maps that fell short take longer.
- **When a song can't carry the dan**, the card says so with a rate to try: «Для этой песни максимум ≈ Gamma mid — попробуй рейт 1.2x (тогда ≈ Delta low)» / "This song tops out at ≈ … — try rate 1.2x", the rate found by the analyser on that map at 1.1–2.0x; or that even 2.0x will not do. Only said once the top rung was tried and nothing went over the range. The card also says when the dan was pulled up («шаг 2 из 3») or the map made lighter; the progress line names the step.
- **«Автоподбор» / "Auto"** beside «Создать карту»: one click decides everything for the loaded song (src/gen/autoPlan.js) and makes the map. The dan: the profile in use (mania-tracker, hand-set or local; the tile of the song's main pattern when there is one, else the overall dan) in the Analysis tab's growth band (−0.1 … +0.5); without a profile, from the tempo and how busy the song is (4–12). Per part, from the stems: loud kick + snare → chordjack (a busy kick → jacks), fast hats → stream, melodic parts → handstream (loud) / jumpstream / tech (quieter); without stems by loudness; quiet parts (and quiet intros, breaks, outros) get an easier range of their own (2 dans lower, at most 8). The model: neural M (or S) with the graphics card and stems, else XGBoost v3 with stems, else Classic; 4 candidates for the critic when critic.json is there; repeats with stems; 1/4 + 1/8 (all grids for a model with a divisor head). It fills the normal controls (dan picker, pattern chips, parts with their patterns and ranges, stamina / bursts, grids, model, candidates, repeats), then generates; a line under the buttons says what it chose («Автоподбор: Gamma mid · дроп — джампстрим, куплет — стрим; модель: нейросеть M», where the dan came from), «изменить выбор» / "edit these choices" hides it and brings the controls into view. No LNs: the generator and the dan analyser are rice only — a part with long sustained sound is named as the reason. The profile is waited for at most 3 s. ru / en.

## 0.9.7

- **Dan by part, «Дан по частям» / "Dan by part"** — a block of its own on the Analysis tab, under the difficulty line; the card's dan is untouched and stays the map's overall dan. The map is cut into parts (src/analysis/sections.js): the notes on the play's clock, a gap of 4 s or more is a break that no part runs over, a stretch up to 40 s is one part, a longer one is cut by dynamic programming where its note density changes most (1 s bins, the parts' squared deviation from their own mean density + a cost per part + a cost for straying from 24 s; parts 12–40 s), each cut moved to the widest gap between notes within 1.5 s. Works the same on any chart (osu! stable, lazer, Interlude's library) without its audio. Each part with 24+ notes is rated by the card's own model (analyzeChart, now with a `minNotes` option) as a chart of its own at the current rate; a part with fewer is a quiet part without a dan.
- **Calibrated for what a part lacks against the whole map** (stamina, length), fitted on the training corpus (tools/calibrate-sections.mjs, read-only on A:/SneezeyTrain; 3359 charts across dans 1–19, 22964 parts; fit on 2/3 of the song groups, error told on the other third): `dan = raw + offset(raw) + lengthGain·ln(24 s / part length) + supportGain·ln(1 + supportSec / 60)` — offset piecewise linear between knots at dans 1, 3 … 19, supportSec how long the map plays within a dan of the part (a lone spike counts less than a hard stretch that goes on); lengthGain −0.29, supportGain +0.53 (src/analysis/sectionCalibration.js). The hardest part against the whole map's dan, held-out: bias −0.11 → −0.02, MAE 0.46 → 0.42, RMSE 0.67 → 0.59, within 1 dan 88% → 93%.
- **Shown** as steps along the map's time (bars coloured by the part's pattern family, the dan names on the axis, the whole map's dan as a dashed line with its key under the chart, the hardest part outlined and named in a chip), the part under the pointer or tapped told below («0:50–1:35 · Epsilon low · 14.6 · Jumpstream · самая сложная часть»), «Все части (7)» / "All parts (7)" unfolds a list of every part (remembered with the ladder's state); «считаем дан каждой части…» meanwhile, failures and maps without any rated part say so. ru / en.
- **Worked out once per map and rate in the background**: the worker's new "sections" job (90 s limit) in the background line, 500 ms after the card (after the details), cancelled when the map changes, cached in the shared result cache under its own key (`#sections1.1`), sent on `analysis-sections` and again after a page reload (app/analysisSections.js). About 0.2 s per map on the corpus (median, 0.6 s at the 95th percentile; ~7 parts) — as much as one more card analysis.
- **Overlay: the Dan widget shows only the map's overall dan** («Сделай чтобы в оверлее был только общий дан»): the dan along the map, its playhead and «сейчас: …» are gone, with their settings toggle, the strain-based estimate (sectionDans, danAt, danProgress, danSparkGeometry) and the details the overlay fetched for it — the widget's source keeps only the card's result per map and rate. The extras (main pattern with the confidence, "for you", "this play") stay as options, **off by default**; the window's size follows the lines shown (220 × 64 for the dan alone). overlay.json gets `v: 2`: a 0.9.6 file has "live" dropped and its extras turned off when none of them had been turned off (never touched), kept as they were otherwise. The settings window, its preview and the made-up payload follow.
- **Marathon: one scroll speed for every map.** osu!mania scrolls relative to a chart's main BPM (the BPM that lasts longest), so in a marathon of maps with different BPMs each map used to scroll at its own speed. Every map's speed is now scaled by the marathon's main BPM / that map's own main BPM (green lines at each red line, the map's own SV changes kept), so each map scrolls in the marathon exactly as it does on its own.

## 0.9.5

- **Mapper style follows the model picked:** the «Стиль маппера» / "Mapper style" list on the Create tab now shows the styles of the model chosen in the picker right away — before anything has been generated with it — instead of the styles of whichever model ran last. Main reads each model file's `styles` once (only that array: the file is scanned in 1 MB chunks up to it, so the 118 MB mapper-xgb3.json is never parsed) and keeps the lists in userData\model-styles.json by file size and change time, so later starts read no model file (app/modelStyles.js); generator-info sends them per choice (`stylesBySize`: auto, xgb3, s, m, l — the file the worker would load for it, LUNACY_MODEL_DIR first). Picking another model keeps the style when that model has it, else sets «Без стиля» / "No style" with a short note. The classic model has no styles: the list stays off and says so («у классической модели нет стилей — выбери XGBoost v3 или нейросеть»).
- **Readable names, sorted, searchable:** the neural nets' styles carry raw keys as names (`n:-beajek-`, `u:13747903`); they are now named from XGBoost v3's list (same keys), else the key without `n:`, and an osu! user id without a name shows as «маппер #<id>» / "mapper #<id>" (src/gen/styleNames.js). The 121 styles are sorted by number of maps, shown as «Name · 288 карт» / "Name · 288 maps", and a search box beside the list filters it by name or key (Enter takes the first match, ↓ goes to the list, Esc clears it).
- **Checked against the chosen model:** generate-map checks a style against the styles of the model its `modelSize` loads (not the model that answered last), so a stale choice can no longer be refused or dropped without a word. The card names the style the map was made with («Стиль маппера: …» / "Mapper style: …"), or says the style was not used when the model that ran has none (e.g. a neural net without the sound breakdown falls back to the classic model).
- **What a style does, measured:** on the same 34 s test song and seeds, a style changes 67–88% of the rows against no style (another seed changes 87–94%), so it really reaches both engines; but over 8 seeds the pattern mix of XGBoost v3 stays within seed-to-seed noise (histogram distance 0.05–0.10 against 0.14 between two seed sets), while the nn-v2 S moves past it (0.05–0.12 against 0.04). The hint under the list says so: little on XGBoost v3, gently on the neural nets.

- **Editor:** the [Mania] section with `Keys: 4` of skin.ini as the osu! wiki documents it, in groups with plain ru/en labels and tooltips (the skin.ini key in each): General (Name, Author); sizes and positions (ColumnStart, ColumnRight, ColumnWidth — one slider for all columns and a box each —, ColumnSpacing, ColumnLineWidth, HitPosition, LightPosition, ScorePosition, ComboPosition, BarlineHeight, WidthForNoteHeightScale, LightingNWidth, LightingLWidth); behaviour (UpsideDown, KeysUnderNotes, JudgementLine, NoteBodyStyle, SpecialStyle, ComboBurstStyle, KeyFlipWhenUpsideDown, NoteFlipWhenUpsideDown, SeparateScore, LightFramePerSecond); colours (Colour1–4 and ColourLight1–4 per column, ColourColumnLine, ColourBarline, ColourJudgementLine, ColourKeyWarning, ColourHold, ColourBreak, with opacity where the key has it); the pictures of every column (KeyImage#, KeyImage#D, NoteImage#, #H, #L, #T as thumbnails, below); the stage (StageLeft, StageRight, StageBottom, StageHint, StageLight, LightingN, LightingL, WarningArrow) and the judgements (Hit300g … Hit0). skin.ini is read and written line by line (src/skin/skinIni.js): what isn't edited comes back byte for byte — comments, spacing, a BOM, CRLF or LF, other sections and other key counts, a non-UTF-8 file kept as its bytes; a `//` comment after a value stays. Undo / redo (a slider drag is one step).
- **Builder:** note shape (circles, bars, arrows that point their column's way, diamonds), column colours with presets (1-2-2-1, 1-2-1-2, one colour, four colours; six colour sets; a colour picker per column), dark or light, column width, note size, hit position, hold bodies (solid, striped, faded; stretched or repeated), keys pressed and not (plain, with an icon, coloured), the stage (no edges, lines, lines and glow), judgements as MAX/300/200… or PERFECT/GREAT… in a bold, thin or pixel font of its own, column light and hit flashes. Every picture is drawn by the app (src/skin/art.js, font.js — no third-party art) at @1x and @2x, written as PNG with node's zlib. On an opened skin it redraws only the parts ticked (notes, holds, keys, stage, lighting, judgements, sizes and name) into a new folder, so undo still has the old pictures; the export takes only the ones skin.ini points at.
- **Your own picture for every element:** every picture of the 4K part — per column the note, LN head, body and tail, the key and the pressed key; the stage's left, right and bottom, the hit-line picture (StageHint), the column light, the hit flash and the hold light, the start arrow; each judgement (MAX/300g, 300, 200, 100, 50, miss) — has a thumbnail: a click («Своя картинка…» / "Own picture…") or a file dropped on it takes a PNG, JPG or WebP, which the tab turns into two PNGs with their transparency (the @1x and an @2x twice its size; a file named …@2x is the @2x and the @1x is made half of it; the @2x kept within 4096 px), written as lunacy-mania\custom\<key>-<time>.png and @2x.png in the working copy and set in skin.ini; «Сбросить» / "Reset" goes back to the picture the skin had when it was opened (or the builder last drew), «Применить ко всем колонкам» / "Apply to all columns" does either for the four columns at once. Checked in main (PNG pair, @2x exactly twice, at most 4096 px and 12 MB); a very large picture is warned about, and in a skin made from scratch so is a note, LN end or key that is not square (Interlude fits it into a square). The preview shows it at once, the .osk carries it, and the Interlude .isk of a skin made from scratch uses it in place of the drawing (fitted into the square frame, a hold body stretched, a hold tail turned over for Interlude's upscroll-first tails; the hit-line picture as the judgement line, the stage edges, column light and flashes switched on when they are the user's). Judgement pictures have no place in an Interlude noteskin; combo and score digits are [Fonts] pictures, not part of [Mania], and are not edited.
- **Live preview:** osu!'s 640 × 480 stage drawn from the skin's own pictures and values — columns at ColumnStart with their widths, gaps and lines, keys (pressed by an autoplay), notes and holds (NoteBodyStyle) falling to HitPosition, the hint and judgement line, column light at LightPosition tinted with ColourLight#, hit flashes and hold light, the judgement at ScorePosition — on a short built-in loop at 170 BPM; downscroll / upscroll, scroll speed. Every edit shows at once.
- **Export:** «Сохранить .osk и открыть в osu!» / "Save an .osk and open it in osu!" writes Documents\Lunacy mania\скины\<name>.osk (never over an older file: "name (2).osk") and opens it, so osu! stable and lazer import it; «Сохранить копию папкой» saves a plain folder copy there. The original skin is never written to.
- **Interlude** (only for a skin made from scratch — an osu! skin is finished in Interlude's own editor, and Interlude can import an .osk itself): a `.isk`, Interlude's own skin package — skin.json and a Noteskin folder with noteskin.json and grid textures (`note[1x4].png`, `holdhead`, `holdbody`, `holdtail`, `receptor[1x8].png`, and with lighting `receptorlighting`, `noteexplosion`, `holdexplosion`; `stageleft`/`stageright`, `judgementline`), re-implemented from Prelude's format (MIT): square frames, one row per column colour, ColumnWidth × 1080/480, enums by name, colours ARGB. Dropped on Interlude's window it is copied into its Skins folder; the app doesn't write there. Interlude has no key images (receptors instead), takes the hit position, scroll direction and judgements from its own settings and ruleset, and has no per-skin judgement pictures in the noteskin.
- **Dan by rate:** the ladder on the analysis card steps by 0.05 (0.9×, 0.95×, 1.0× … 1.5×) instead of 0.1.
